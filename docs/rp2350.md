# RP2350 / Raspberry Pi Pico 2

What the chip actually offers, focused on the parts that matter when you're emulating a sensor bus. Figures here are taken from the pico-sdk headers (`src/rp2350/hardware_regs/include/hardware/platform_defs.h`) rather than marketing pages.

## At a glance

| | RP2350A (Pico 2) |
|---|---|
| Cores | 2 × Cortex-M33 @ 150 MHz, *or* 2 × RISC-V Hazard3 |
| SRAM | 520 KB |
| Flash (on Pico 2) | 4 MB external QSPI |
| **PIO** | **3 blocks × 4 state machines = 12** |
| **PIO instruction memory** | **32 instructions per block**, shared by that block's 4 SMs |
| DMA | 16 channels |
| GPIO | 30 (RP2350A) / 48 (RP2350B) |
| Hardware I²C / SPI / UART | 2 / 2 / 2 |
| PWM slices | 12 |
| USB | 1.1 full-speed (12 Mbit/s) device or host |
| ADC | 12-bit, 5 channels (RP2350A) |
| DAC | **none** |
| Crystal | 12 MHz |
| Spinlocks | 32 |

**Not 5 V tolerant.** Level shifting is required for 5 V targets.

## Timing, in cycles

At 150 MHz one cycle is **6.67 ns**. That number governs everything about bit-banging a bus:

| Bus rate | One bit period | Cycles available |
|---|---|---|
| I²C 100 kHz (Standard) | 10 µs | ~1,500 |
| I²C 400 kHz (Fast) | 2.5 µs | ~375 |
| I²C 1 MHz (Fast-mode Plus) | 1 µs | **~150** |

150 cycles is the real budget for anything that must happen inside one SCL period. It is comfortable for shifting bits and impossible for a table lookup plus a decision — which is why clock stretching exists as a design tool, not just a protocol quirk.

## Memory

```
0x10000000  XIP — memory-mapped external flash (4 MB on Pico 2)
0x20000000  SRAM, 520 KB total
```

The 520 KB is not one flat block:

- **512 KB** as 8 × 64 KB banks, **striped** across the address range `0x20000000`–`0x20080000`. Striping interleaves consecutive addresses across banks, so two bus masters (the two cores, or a core and DMA) accessing nearby addresses tend to land in different banks and don't contend.
- **8 KB** as two 4 KB banks at `0x20080000` and `0x20081000`, outside the striped region. Because they're separately addressed, they're useful for giving one core or DMA a private scratch area with guaranteed no contention.

Code executes from flash via XIP with a cache. **XIP access is not deterministic** — a cache miss stalls for a flash read. Anything with hard timing requirements should run from SRAM; the SDK offers `__not_in_flash_func()` for exactly this.

## Two cores

Both cores are equal — there is no "main" core. `multicore_launch_core1()` starts the second one.

They can communicate through:

| Mechanism | Notes |
|---|---|
| **SIO FIFOs** | A hardware 8-entry FIFO each way. Fast, but blocking, and easy to deadlock if both sides push simultaneously. |
| **Doorbells** | 8 inter-core interrupt lines (new in RP2350). Signal without moving data. |
| **Spinlocks** | 32 hardware spinlocks. Correct, but any lock on a real-time path is a latency risk. |
| **Shared SRAM** | Fastest, and the only option with no blocking — but ordering and cache coherence are yours to get right. |

A lock-free single-producer/single-consumer ring buffer in shared SRAM is usually the right structure for streaming data between cores, because it never blocks either side.

The Cortex-M33 brings a single-precision FPU, DSP instructions, and TrustZone-M security extensions over the M0+ in RP2040.

## PIO — the reason this chip is interesting

PIO ("Programmable I/O") is a set of tiny deterministic processors that drive pins directly. It is not a bit-banging library — it is real hardware that runs independently of the CPU with cycle-exact timing.

### Structure

```
RP2350
├── PIO0 ── 32 instructions shared ── SM0 SM1 SM2 SM3
├── PIO1 ── 32 instructions shared ── SM0 SM1 SM2 SM3
└── PIO2 ── 32 instructions shared ── SM0 SM1 SM2 SM3
```

**The 32-instruction limit is per block, not per state machine.** This is the single most important constraint to internalise. Four state machines in one block *share* one 32-instruction memory. So:

- Four SMs running the *same* program in one block: nearly free.
- Two SMs running *different* programs: both programs must fit in 32 instructions together.

You will run out of instruction memory long before you run out of state machines.

### What a state machine has

- A **PC**, and its own clock divider (fractional, from the system clock)
- Two 32-bit scratch registers, **X** and **Y**
- An **output shift register** (OSR) and **input shift register** (ISR), each with configurable shift direction and an autopush/autopull threshold
- A 4-entry **TX FIFO** and 4-entry **RX FIFO**. If a program only reads or only writes, the two can be joined into a single 8-entry FIFO in the used direction.

### The instruction set — nine opcodes

```
JMP   WAIT   IN   OUT   PUSH   PULL   MOV   IRQ   SET
```

Every instruction is **one cycle**, plus an optional delay of 0–31 cycles encoded in the same word. That makes cycle counting exact: a loop's timing is readable straight off the listing.

Two features that cost you elsewhere:

- **Side-set** lets an instruction change pins *at the same time* as doing its main job — indispensable for driving a clock line. But side-set bits are taken from the same field as the delay, so using side-set reduces the maximum delay you can encode.
- **`IRQ`** can raise a flag that either stalls another state machine or interrupts a CPU core, which is how PIO hands a decision back to software.

### Driving open-drain buses

I²C never drives a line high — devices only pull low, and an external resistor pulls the line up. In PIO you achieve this by writing the output register to `0` once, then manipulating **pin directions**:

```
SET PINDIRS, 1   ; pin becomes an output driving 0 → line pulled LOW
SET PINDIRS, 0   ; pin becomes an input          → line released HIGH
```

Both SDA *and* SCL need this treatment: clock stretching means a device holds SCL low, which is the same mechanism.

### Where PIO ends

PIO has no arithmetic beyond decrement-and-branch on X/Y, no memory access, and no comparisons other than zero-testing. Anything that requires a lookup, a table, or a real decision belongs on a CPU core, with PIO stalling until the answer arrives — usually via `IRQ` to signal, then blocking on `PULL` to receive.

That split — PIO for exact timing, CPU for decisions — is the shape of nearly every non-trivial PIO design.

## Other peripherals

**DMA — 16 channels.** Tightly integrated with PIO: a channel can be paced by a state machine's FIFO, so PIO can stream to or from memory with no CPU involvement. Channels can chain to one another for continuous capture.

**PWM — 12 slices**, each with two channels. Prefer these over PIO for plain PWM output; state machines are the scarcer resource.

**USB — 1.1 full-speed only** (12 Mbit/s), with 4 KB of dedicated packet RAM. Fine for a CDC serial link. This is a real ceiling if you plan to stream bulk data to a host.

**ADC — 12-bit, 5 channels** on RP2350A. Note there is **no DAC**: analog *output* requires external silicon, and a resistive sensor needs a digital potentiometer rather than a DAC, because the target's own divider is part of the circuit.

| | |
|---|---|
| Chip | RP2350A |

| Exposed GPIO | 26 of the chip's 30 |

| USB | micro-USB B |
| Default I²C0 | SDA GP4, SCL GP5 |
| Default SPI0 | SCK GP18, TX GP19, RX GP16, CS GP17 |
| Default UART0 | TX GP0, RX GP1 |

> On **Pico 2 W** the LED is driven through the wireless chip rather than a GPIO, and GP23–25 and GP29 are consumed by it. For pin-hungry work the non-W board gives you more to play with and a simpler first blink.

## Gotchas

- **Not 5 V tolerant.** Level shift anything above 3.3 V.
- **RP2350 has published errata**, including documented GPIO input behaviour affecting pull-down configurations. Check the current list against your pad setup and validate empirically rather than assuming.
- **Flash execution is not deterministic.** Put timing-critical code in SRAM.
- **Both cores share one flash cache.** Heavy XIP traffic on one core perturbs timing on the other.
- **RP2350's PIO is not identical to RP2040's** — it adds capabilities. Verify instruction behaviour against the RP2350 datasheet rather than RP2040 experience.
